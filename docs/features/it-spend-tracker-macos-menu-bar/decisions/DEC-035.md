## Context

The user needs Gemini usage per API key («мне важно по ключам тоже знать»). Google's billing export has no per-key cost; Cloud Monitoring reports request counts per key (`serviceruntime.googleapis.com/api/request_count`, resource `consumed_api`, label `credential_id = apikey:<uid>`). The user also asked that every service link to the provider console where keys can be changed or disabled.

## Decision

The Google Cloud connector lists API keys (API Keys API v2) of the projects given in "Projects with API keys" and reads, per key, the month-to-date request count from Cloud Monitoring. Keys show name, project, allowed APIs, creation date and requests this month; cost stays per project and model (no per-key cost is estimated). The service account gets only API Keys Viewer and Monitoring Viewer on those projects. Every service page links to the provider's billing and key-management consoles, and every key links to its own console page where the provider has one (otherwise to the keys list).

## Reason

The user chose "keys + requests per key" and asked for console links everywhere.

## Consequences

The API Keys and Cloud Monitoring APIs must also be enabled in the service account's own project, because Google attributes the calls to it; the OAuth token needs `cloud-platform.read-only` (API keys) and `monitoring.read` (Monitoring does not accept the generic read-only scope). If request counts cannot be read they show as unavailable with a note, never as zero. Per-key request counts are available only as far back as Cloud Monitoring keeps them (about six weeks), so only the current month is shown.
