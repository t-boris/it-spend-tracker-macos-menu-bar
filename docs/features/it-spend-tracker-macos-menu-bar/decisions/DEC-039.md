## Context

History was monthly only (REQ-004). The user wants to see the last 30–60 days in detail, the direction of spend and an expected total for the current month.

## Decision

Per service, the forecast for the current month is:

- usage reported per day: actual usage of the month's past days + for today the larger of today's partial usage and the run rate + run rate × the days left. The run rate is the average daily usage of the last 14 full days (days before provider coverage are not counted). Month days before coverage are filled with the run rate;
- usage booked per month (Neon, GitHub — `dailySpend = false`; GitHub's yearly usage report returns one item per month): during the first 7 days of the month the larger of last month's usage and the usage so far, afterwards month-to-date usage extrapolated at its pace (× days in month / days elapsed);
- plus every subscription charge due in the month (known in advance) and, for manual services, recorded credit purchases.

A connected service without any covered full day (or month) has no forecast; it is listed as such and left out of the total. The forecast is shown with "≈".

For day-level views, usage booked per month is spread evenly over the month's covered days (through today for the current month), so a monthly amount does not appear as a one-day spike. Period comparisons use full days only (through yesterday), because today's provider buckets are incomplete. A period a service's data does not cover completely is "no data" for that service; the total change compares only services with data for both periods and names the ones left out (e.g. a provider whose API returns data only from a later start date), while the period total itself includes every service with data for it.

## Reason

A short run rate follows recent changes (a new model, a new project) while smoothing single-day spikes; subscriptions are known and should not be extrapolated. The method is simple enough to explain in one sentence on the page.

## Consequences

Checked on day 1 of a month on a copy of a real store: the forecast stayed close to the previous month's total, and services booked per month were forecast from last month instead of from a few hours of the new month.

The forecast is approximate and lags sudden changes by a few days. Single large one-off usage days within the last 14 days raise the forecast.
