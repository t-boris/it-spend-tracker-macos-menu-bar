## Context



## Alternatives

1. Only a tag page, no chart on the Tags tab
2. Only the comparison chart on the Tags tab, no tag page
3. Membership counts only from the date a tag was assigned
4. A separate feature and pull request on top of the tags work

## Decision

Historical tag reporting, which the first scope excluded, is now part of this feature. For the last 12 months (the same range as the history page) the app shows the spend of every tag. A tag applies to the whole history: an assignment has no start date, so a target tagged today counts for every month that has data. Each month is calculated with the same rules as the current month (DEC-034, DEC-035, DEC-037): a tagged service counts once and covers its tagged children, targets are added only when provably disjoint, and an unresolved overlap makes that month's total unavailable. A month without any data says so and is never drawn as zero. The history is shown in two places: a page for each tag, opened from the Tags tab, with a chart stacked by service, a month-by-service table and the monthly history of every tagged target; and one chart on the Tags tab with a line for every tag. The lines are not stacked because the totals of different tags may overlap.

## Reason

The user said the tags are projects and asked for more than current-month information: how much went to each project, its history and general charts. In the question dialog the user chose the tag page plus the comparison chart, left the retroactive membership and the per-month rules as proposed, and chose to deliver this inside this feature and its pull request.

## Consequences

The Scope of this feature and the statement of REQ-020 no longer exclude history; REQ-023 (tag page) and REQ-024 (tags over time) are added. History uses only the data stored for each month, so months before a target's data begins show no data. Because membership is retroactive, tagging or untagging changes the past figures of that tag. Tag totals still do not add up across tags.
