## Context

Tags are stored today as KeyTagRecord (key ID plus tag list) under a tracked service (main-feature DEC-024). Assignments must cover services, keys, breakdown items and Neon projects, survive refreshes (which replace key and breakdown rows), and keep existing key tags without loss. The app has no versioned schema; additive models are migrated by SwiftData automatically.

## Alternatives

1. Add kind/scope fields to the existing key-tag record and keep its name (misleading type name)
2. Store tags on the key and breakdown rows (lost on every refresh)

## Decision

A new record kind, one per tagged target, holds: target kind (service, key, breakdown item, usage project), scope (dimension for a breakdown item, organization for a usage project, empty otherwise), reference (provider key ID, exact label, project name; empty for the service), the last known display name, and the tags. Records belong to the tracked service and are deleted with it. Identity is service + kind + scope + reference; the month is never part of it. On launch every legacy key-tag record is converted once into an assignment of kind key and then removed; the conversion is idempotent. The display name is stored when tags are edited and used only while a target is missing.

## Reason

Assignments stay independent of the refreshed rows (a refresh cannot delete them), identity matches AC-003, and a stored name lets a missing target still be shown and edited.

## Consequences

The legacy record type stays in the schema, empty, because removing a model would need a versioned migration. Marked proposed: a technical choice made by the AI within I-1.
